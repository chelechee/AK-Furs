# AK Furs — расчёт ответов по тестовому заданию

Одна команда превращает четыре разрозненные выгрузки в `answers.json`, записку руководителю и ответ клиентке: считает уникальные заказы, сверяет оплаты с банком, находит продажи ниже минимальной цены, проверяет порядок «цена → приглашение» в переписках и собирает Q5 из тех же данных.

Расчёт детерминированный: одинаковый вход даёт побайтово одинаковый выход. Обращений к LLM в числовом тракте нет. Q4 — эвристический предварительный отбор; новые или неоднозначные чаты должны быть подтверждены человеком.

## Требования к окружению

- Python 3.10 или новее (проверено на 3.14).
- Зависимости: `openpyxl` для чтения книги Excel; `pytest` для тестов; `python-docx` для формирования и оформления Q5 в Word.
- Для RAR-архива нужен `UnRAR.exe` из установленного WinRAR. Если его нет, распакуйте чат-файлы `.txt` в `data/`.
- Установка: `pip install -r requirements.txt`.

## Запуск

Из корня проекта:

```
python solve.py
```

Команда берёт входы из `data/`, создаёт при отсутствии выходной каталог `handoff/` и пишет туда три актуальных результата: `answers.json`, `Q5.md` и `Q5.docx`.

```text
OK: handoff\answers.json written with Q5.md and Q5.docx (5949 bytes, SHA-256 ad216700...)
```

Входную папку или zip-архив можно передать первым аргументом, путь к `answers.json` — флагом `--out`. Файлы Q5 создаются рядом с JSON:

```powershell
python solve.py "C:\Downloads\Новая выгрузка"
python solve.py "C:\Downloads\dataset.zip" --out handoff\answers.json
```

Имена файлов и расширения не важны: роль каждого входа определяется по содержимому — CRM по набору колонок заказа, выписка по заголовкам операций, книга Excel по четырём таблицам справочника (в том числе на скрытых листах), переписки по формату сообщений в ZIP/RAR или отдельных `.txt`. Несколько отдельных чат-файлов в `data/` объединяются в один источник. Для RAR используется установленный WinRAR `UnRAR.exe`; файлы извлекаются в память, на диск архив не распаковывается. Если роль не определяется или подходит несколько наборов, команда останавливается с ошибкой и списком кандидатов:

```text
ERROR: ValueError: multiple candidate input files found under C:\выгрузка: crm: a\заказы.dat, b\заказы.dat
ERROR: FileNotFoundError: could not identify all input files by content under C:\выгрузка (missing: chats; not recognized: notes.txt)
```

Структура выгрузки не додумывается: если в CRM переименовали колонку, файл не будет угадан, и команда сообщит, какой роли не хватает.

В каталоге `data/` на исходном наборе лежат четыре файла; имена сохранены только для удобства:

```
data/01_crm_orders_export.csv
data/02_bank_statement_rub.csv
data/03_catalog_prices_reference.xlsx
data/04_client_chats.zip
```

Каталог `data/` в репозиторий не входит: исходные данные не публикуются. Чаты можно оставить в RAR/ZIP либо распаковать в `.txt` прямо в `data/`.

То же самое через PowerShell-обёртку, которая сама обрабатывает пробелы и кириллицу в пути:

```powershell
.\run.ps1 "C:\Downloads\dataset.zip"
```

Если PowerShell блокирует выполнение скрипта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run.ps1 "C:\Downloads\dataset.zip"
```

`python solve.py` уже формирует актуальные `Q5.md` и `Q5.docx` в `handoff/`. Для обновления их корневых копий отдельно:

```powershell
python tools/build_q5.py
```

Скрипт считает показатели, цену и скидку по выгрузкам; часы работы 10:00–21:00 берутся из утверждённого шаблона. Клиентские сведения из C0010 используются только после проверки связи чата с CRM. Если C0010 отсутствует, скрипт явно отмечает, что ответ не сформирован и его нельзя отправлять. Даты обеих частей ставятся на текущий день; для прогона на другую дату есть флаг `--date DD.MM.YYYY`.

Только даты, без пересборки текста, обновляет команда:

```powershell
python tools/refresh_q5_date.py
```

Проверка актуального Q5 из `handoff/` (или корневых файлов, если результатов расчёта ещё нет) и совпадения Word с Markdown:

```powershell
python tools/check_q5.py
```

При ошибке печатается причина и возвращается код 1:

```text
ERROR: NotADirectoryError: data directory not found: data
```

Корневой `answers.json` — контрольный снимок исходного набора; он не перезаписывается запуском и обновляется только осознанно, флагом `--out answers.json`.

> В Windows PowerShell 5.1 перенаправление `>` перекодирует вывод в UTF-16, и файл перестаёт читаться как UTF-8. Поэтому `python solve.py` пишет файл сам, в UTF-8 без BOM, и перенаправление не нужно.

## Структура проекта

| Каталог | Назначение | В Git |
|---|---|---|
| `data/` | только локальные входные файлы выгрузки | нет |
| `handoff/` | актуальные результаты расчёта: `answers.json`, `Q5.md`, `Q5.docx` | нет |
| `employer_package/` | комплект письма по ТЗ: ответы, `Q5.docx`, примеры ошибок агента, скриншоты | нет |
| корень репозитория | код, тесты, `Q5.md`/`Q5.docx` (собираются из данных), контрольный `answers.json` | да |

Разделение зафиксировано в `.gitignore`: входные CSV/XLSX/ZIP, результаты расчёта и материалы отправки в репозиторий не попадают. Корневой `answers.json` остаётся контрольным снимком исходного набора, а не результатом последнего запуска.

`python solve.py` обновляет JSON и оба файла Q5 одним прогоном. `python tools/build_q5.py` по-прежнему позволяет отдельно собрать корневые `Q5.md`/`Q5.docx`; `python tools/package_submission.py` собирает `employer_package/` из проверенных материалов. Текст письма в репозитории не хранится.

## Выходной файл

`answers.json` строго соответствует шаблону задания: ровно десять ключей, без служебных полей. Файл с результатом на исходной выгрузке включён в репозиторий; его можно пересобрать командой выше.

| Ключ | Тип | Смысл |
|---|---|---|
| `q1_unique_orders` | целое | уникальных заказов после очистки |
| `q1_unique_order_lines` | целое | уникальных строк заказов |
| `q2a_paid_orders_without_payment` | массив целых | заказы «Оплачен» без поступлений, по возрастанию |
| `q2b_unidentified_payments_count` | целое | неопознанных поступлений |
| `q2b_unidentified_payments_sum_rub` | JSON-число | точная сумма в рублях; копейки сохраняются, если они есть |
| `q3_price_violation_lines_total` | целое | строк ниже минимальной цены |
| `q3_price_violation_lines_by_manager` | объект | разбивка по каноническим именам менеджеров |
| `q4_chats_meeting_before_price` | массив строк | ID чатов с приглашением раньше цены, по возрастанию |
| `run_command` | строка | команда пересчёта |
| `notes` | строка | зафиксированные трактовки |

Перед выводом результат проходит валидатор: проверяются состав ключей, типы, конечность и неотрицательность сумм/счётчиков, уникальность и сортировка ID, сумма разбивки Q3 и непустые `run_command` / `notes`. Денежный итог суммируется через `Decimal`; сериализация сохраняет десятичное значение без промежуточного `float`.

### Как прочитать `notes` в PowerShell 5.1

`answers.json` записан в UTF-8 без BOM. `Get-Content` в PowerShell 5.1 по умолчанию читает файл как ANSI, поэтому кириллица в `notes` выглядит как `РќРѕРјРµСЂ...`. Это не повреждение JSON, а кодировка чтения. Используйте:

```powershell
(Get-Content .\answers.json -Encoding UTF8 -Raw | ConvertFrom-Json).notes
```

Если консоль всё равно не отображает кириллицу, скопируйте текст в буфер:

```powershell
(Get-Content .\answers.json -Encoding UTF8 -Raw | ConvertFrom-Json).notes | Set-Clipboard
```

Либо прочитайте через Python:

```powershell
python -c "import json; print(json.load(open('answers.json', encoding='utf-8'))['notes'])"
```

## Тесты

```
python -m pytest tests -q
```

257 тестов, покрытие пакета `akfurs` — 86% строк и ветвей (замер: `python -m coverage run --branch --source=akfurs -m pytest tests -q`; два теста RAR пропускаются для ZIP-входа, ещё один тест отсутствия C0010 — когда этот чат присутствует). Покрытие не считается доказательством бизнес-корректности. Набор включает:

- юнит-тесты разбора номеров, дат, цен, скидок и статусов;
- интеграционные тесты на реальной выгрузке: дедупликация, границы периодов прайса, извлечение номеров из назначений;
- метаморфные: данные переписаны в другой кодировке, разделителе, порядке колонок или формате даты — ответ обязан совпасть;
- мутационные: изменение данных обязано сдвинуть ответ предсказуемо (закрыли оплату, добавили неопознанный платёж, добавили строку ниже минимума);
- негативные: повреждённый вход обязан дать понятную ошибку, а не тихий пропуск;
- adversarial: номер модели/бюджет клиента вместо цены, отрицание и цитата приглашения, равные timestamps, номер заказа, совпавший с суммой, счёт/договор, точные копейки и конфликтующая ничья при дедупликации;
- интерфейс и структура: переименованные входы, неоднозначный комплект, путь с кириллицей и пробелами, zip-вход, создание `handoff/`, отсутствие угадывания изменившейся структуры;
- Q5: правило эмодзи на обоих случаях, наличие обеих дат, синхронность Markdown и Word, сборка комплекта письма;
- генерация Q5: все числа берутся из данных, изменение цифр меняет текст, устаревшая цифра ловится проверкой, статические фрагменты шаблона не содержат чисел.

Тесты, требующие исходных данных, пропускаются, если каталог `data/` отсутствует.

## Принятые допущения

Полный разбор — в [ASSUMPTIONS.md](ASSUMPTIONS.md). Кратко:

- номер заказа приводится к целому, кириллица и латиница не различаются;
- строка заказа — пара «номер + № строки», побеждает максимальное «Выгружено»;
- статус определяется только полем «Статус», комментарий его не меняет;
- в датах `ДД/ММ/ГГГГ` первым идёт день (проверено тремя способами);
- при двух разделителях в цене десятичный — правый;
- переименования артикулов применяются без учёта даты перехода;
- Q2a: заказ оплачен, если оплачена хотя бы одна строка;
- Q3: исключён только «Отменён», «Возврат» участвует;
- Q4: чат без названной цены считается нарушением;
- роль входа определяется по содержимому, изменившаяся структура не угадывается;
- Q5b: один фирменный ✨ в приветствии; для других ответов действует политика эмодзи библиотеки;
- Q5: даты стоят в обеих частях и совпадают в Markdown и Word.

## Известные ограничения

- Если в новой версии данных платёж будет содержать два разных существующих номера заказа, программа остановится с ошибкой неоднозначности: правило приоритета в задании не задано.
- Если в наборе нет чата C0010, Q1–Q4 и записка формируются, но клиентский ответ не генерируется; в Q5 выводится предупреждение о недостающей переписке.
- Если в новой выгрузке переименована колонка или добавлена таблица, роль файла не определится: расчёт остановится с указанием, какой роли не хватает. Молчаливого выбора «похожего» файла нет.
- Извлечение номера платежа использует явные метки заказа и коды; номер счёта трактуется как номер заказа только по обнаруженной конвенции текущей выписки (347 из 347 ссылок на счёт совпадают с CRM). Другие номера документов, суммы, даты и телефоны исключаются; конфликт заказа и счёта останавливает расчёт. Новую банковскую конвенцию нужно подтвердить до принятия Q2.
- Если Q4 распознал новую формулировку неверно или не распознал её, автоматический список нельзя принимать без человеческой проверки. Маркер приглашения/цены не является полноценным семантическим анализом.
- Формулы в книге Excel должны быть пересчитаны до выгрузки: без кэшированных значений цены прочитать нельзя, и это явная ошибка, а не тихий пропуск.
- Незнакомый формат чата приводит к явной ошибке без печати текста переписки в сообщение ошибки.
- В исходном 150-чатовом эталоне вручную проверено 22 ID; новые формулировки требуют отдельной проверки.
- Чат без приглашения менеджера не считается нарушением и просто не попадает в `q4`; расчёт продолжается.
- `q3_price_violation_lines_by_manager` содержит только менеджеров с нарушениями; нулевые значения не добавляются.

## Куда двигать проект

Порядок действий, когда новая выгрузка не подошла:

1. Запустить `python solve.py` и прочитать точный текст ошибки.
2. Отнести изменение к одному из трёх классов:
   - **косметика** — значение то же, запись другая: расширять разбор, добавляя тест на конкретное значение;
   - **структура** — переименованы колонки, другая книга, другой формат чатов: не угадывать, согласовать структуру;
   - **смысл** — правило не задано (два заказа в одном платеже, ничья в дедупликации): сформулировать правило, записать в `notes`, только потом кодировать.
3. После правки прогнать весь набор и убедиться, что ответы на исходной выгрузке не изменились.

Ближайшие безопасные расширения — каждое отдельным тестом:

- двузначный год в датах (`01.01.25`) с зафиксированным правилом века;
- часовой пояс в дате-времени (`2026-10-01T09:42:00+03:00`);
- лишние кавычки и пробелы вокруг значений;
- UTF-16 без BOM;
- явный тест на табуляцию как разделитель;
- несколько листов с одинаковой таблицей — брать первый и фиксировать это в `notes`.

Чего не делать: подбирать колонку по похожести названия, считать первое число в назначении номером заказа, молча выбирать один из двух заказов, ослаблять разбор чатов. Такие послабления дают правдоподобные, но неверные цифры.

## Чек-лист перед отправкой

1. `python solve.py` — код возврата 0, в выводе путь и SHA-256.
2. `python -m pytest tests -q` — полный набор зелёный.
3. `python tools/build_q5.py` — записка и ответ клиентке пересобраны из текущих данных, даты обеих частей на текущий день.
4. `python tools/check_q5.py` — Q5 совпадает с данными, правилом эмодзи и Word с Markdown.
5. `python tools/package_submission.py` — комплект собран, ответы совпадают с `handoff/answers.json`, даты обновлены.
6. `git status` — в изменениях только код, тесты и документы; `data/`, `handoff/`, `employer_package/` отсутствуют.
7. `git diff --cached --stat` — ни один CSV, XLSX или ZIP из выгрузки не попал в staged.
